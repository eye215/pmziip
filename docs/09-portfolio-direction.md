# 제품 방향: PM 성과 포트폴리오

기준: 2026-11-26. 현재 구현은 [서비스 IA·기능명세·데이터구조](08-service-ia-spec.md)를 따른다.

PM.zip의 최종 산출물은 '과제 한 건 = 케이스 스터디 한 장'이다. 이를 모아 기간별 성과 보고서와, 회사 밖에 보여 줄 수 있는 공개용 포트폴리오를 만든다. 어느 회사를 가든 같은 흐름으로 쓴다.

## 흐름과 현재 상태

| 단계             | 남길 것                                       | 현재                                                                       |
| ---------------- | --------------------------------------------- | -------------------------------------------------------------------------- |
| 1. 수집          | 요구사항 원문과 출처(메일·Slack·붙여넣기)     | 있음                                                                       |
| 2. 결정          | 할지·보류·안 함, 사유, 대안, 목표월           | 칸은 있으나(`decisionReason`, `alternative`, `targetMonth`) 결정 화면 없음 |
| 3. 변경 기록     | 기획서 링크, 사이트 주소, 전·후 화면, 바뀐 점 | 없음                                                                       |
| 4. 사용 예측     | 사용자가 어떻게 쓸지, 예상 막힘 지점          | 측정 계획의 가설 칸만                                                      |
| 5. 실제 사용     | 배포일 기준 전·후 지표, 예측 적중 여부        | GA 월별 합계만                                                             |
| 6. 비즈니스 연결 | 제품별 판매·매출 지표와의 동반 변화           | 없음(공시는 회사 전체 단위)                                                |
| 7. 회고          | 아쉬운 점, 다음에 다르게 할 것 → 새 요구사항  | 없음                                                                       |
| 8. 성과 보고서   | 기간 요약 + 케이스 스터디, 확정 시 스냅샷     | 없음                                                                       |

## 원칙

- **회사 기록과 공개용을 나눈다.** 원본은 회사 안에 두고, 포트폴리오는 회사·고객명과 내부 링크를 빼고 절대 수치를 변화율·지수로 바꾼 내보내기로만 만든다.
- **관찰과 해석을 나눈다.** '배포 후 사용이 늘고 판매도 늘었다'는 관찰이고, '그 때문에 팔렸다'는 해석으로 따로 적는다(AGENTS.md: 추측을 사실로 저장하지 않음).
- **내 기여를 밝힌다.** 과제의 기여(`contribution`) 칸에 기획·데이터·협업 중 내가 한 범위를 적는다.
- 확정한 성과 보고서는 스냅샷으로 저장하고 고치지 않는다(새 버전으로만).

## 만드는 순서

1. 과제를 케이스 스터디 화면으로: 결정·변경 기록·예상 막힘·회고 칸
2. 배포일 기준 전·후 비교(GA), 예상 막힘 지점과 실제 대조
3. 기간 성과 보고서와 확정 스냅샷
4. 익명화된 공개용 내보내기
5. 판매 데이터 연결(출처와 회사 승인 확인 후)

## 포트폴리오에 담을 것

케이스 스터디 한 장은 아래 여덟 줄로 쓰고, 각 줄은 PM.zip에 쌓인 기록에서 나오게 한다.

1. 문제: 누가 어디서 막혔나, 근거 원문 몇 건·어느 채널
2. 결정: 왜 했는지(또는 안 했는지), 버린 대안, 우선순위 근거
3. 내 역할: 내가 한 일과 함께한 사람의 역할
4. 변경: 전·후 화면과 기획 요지
5. 가설: 예상 사용 방식과 막힘 지점
6. 결과: 사용 지표 전·후 변화율, 예측이 맞았는지
7. 비즈니스: 판매·매출 지표의 동반 변화(인과 아님을 명시)
8. 회고: 아쉬운 점과 다음에 다르게 할 것

포트폴리오 감으로 특히 좋은 것:

- 안 하기로 한 결정과 그 이유. 버리는 판단이 PM 역량의 가장 강한 증거다.
- 데이터로 우선순위를 바꾼 사례. 요구사항 건수·사용 지표가 순서를 어떻게 바꿨는지.
- 측정 체계를 만든 일. 예: Galaxy Coach에서 완료(REPORT)와 유효 점수를 나눠 세고 UU를 합산하지 않게 정의한 것.
- 예측이 틀린 사례와 배운 점. 성공담만 있는 포트폴리오보다 믿음이 간다.
- 일하는 방식을 바꾼 도구. 메일·Slack 요구사항을 자동으로 모으는 PM.zip 자체도 사례가 된다.
- 기간 요약 숫자: 수집 건수, 결정 건수(안 함 포함), 배포 수, 측정 계획 수립률, 지표가 개선된 과제 수.

주의: 회사 데이터(수치·화면·고객명·내부 문서)를 그대로 들고 나가면 보안 규정·계약 위반이 될 수 있다. 공개 전 회사 규정을 확인하고, 익명화된 내보내기만 쓴다.
